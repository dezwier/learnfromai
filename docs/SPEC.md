# Adaptive Mastery

Sign in, then explore one shared knowledge graph grown by an LLM neighborhood around each focus topic.

## Product

- Authentication uses Firebase. The API exchanges a Firebase ID token for its own JWT.
- There is one shared topic graph. A search merges into that universe; it does not create a private graph.
- A node has a UUID, canonical `name`, `name_key`, a standalone `description`, and an optional shared iconic `image_url` (PNG bytes generated or uploaded on demand). Names are not globally unique when the model says two same-titled topics are different concepts.
- Edges are typed `parent`, `child`, `sibling`, or `acquaintance`, and are stored in both directions.
- Neighborhood size is global (not per-user): expand aims for 16 direct neighbors; the canvas targets at most 30 tiles (focus + directs + extended). Every direct neighbor is always shown (even if that exceeds 30); neighbors-of-neighbors top up the rest (max 14). The model chooses how many parents, siblings, children, and acquaintances to return (a bit of each; usually most children).
- Focusing or opening a topic returns whatever neighbors already exist (`incomplete` when under the user’s total budget). A Railway worker runs `expand_neighborhood` when the user explicitly requests neighbors, and a separate daily Railway cron may also enqueue shared expand/content jobs from ranked affinity (defaults: 5 neighbor + 10 learn per day). Cron only enqueues; the always-on worker runs the LLM work.
- Expand uses two reusable LLM prompts plus deterministic retrieve: `neighborhood_v6` (invent related topics for the deficit, excluding existing neighbor titles; model picks the parent/sibling/child/acquaintance mix) and `sameness_v3` (batched same-concept? → id or null). Atomic learning uses `content_bits_v6` separately (short title + interesting learning bit; cloze is one-word multiple choice).
- Scenarios: (1) new topic → retrieve → sameness → exists → under budget → neighborhood → retrieve/sameness per result → write; (2) new → retrieve → sameness → not exists → neighborhood → …; (3) existing focus → under budget → neighborhood → …; (4) new → retrieve → sameness → exists → budget met → Done; (5) existing focus → budget met → Done. Existing-tile expand skips focus sameness.
- Each topic can have many shared **learning atoms**. One atom is stored as `learn` plus one or more of `check1` / `check2` / `check3` (`pack_index`; existing rows are atom `1`). Content-complete means learn + **at least one** playable check (fewer than three is fine; zero checks → atom is removed). Check types: `mc` (question + 4 choices), `true_false` (statement), `cloze` (blank prompt + 4 one-word choices). Free-text cloze is deleted. For the learner, an atom is **complete** after `learn` + **any one** check (randomly chosen); quiz results stay in `user_topic_events` and, once complete, enroll the atom in the Leitner **testing track** (`user_pack_reviews`). Atoms are generated on demand via `expand_content`. `POST …/content` with `{expand: true, new_pack: true}` adds another atom only when every existing atom is content-complete. Generation avoids overlapping prior atoms on the topic; the content prompt lists no neighbor titles and requires each atom stay clearly about this topic. Bits are cached on the node for all users. Legacy kinds `example` and `check` may still exist; `check` is treated as `check1`. Legacy check bodies without `type` are treated as `mc`. Each atom may also have an optional shared **atom image** (`knowledge_pack_images`); learn cards show atom image when present, otherwise the topic iconic image.
- **Learning track:** tapping the focus tile opens a single-card path always scored from that opening focus. First card (`opening=true`): a random atom on the focus (prefer unlearned; else replay a learned atom; else generate on the focus). While each card is shown, the client prefetches the next via weighted dice from the focus (`LEARN_TRACK_P_FOCUS`/`_CHILD`/`_OTHER`, defaults 0.4 / 0.3 / 0.3 — empty buckets drop out and weights renormalize): pick the focus, a random child, or a random other direct neighbor, then an unlearned atom on that tile or `generate` for it (background expand so Next can land ready). Quiz face picks a random check. Next advances using the prefetched card; the seed never wanders — every pick stays relative to the opening focus. Long-press on a learn card opens an **atom action drawer** (generate/upload atom or topic image; admins also get delete quiz/atom). Topic long-press → action drawer → **Show atomic learning** opens the multi-atom review deck for that topic only.
- **Testing track (Leitner):** a graph FAB opens the hub with bin distribution (1–2 learning, 3–4 familiar, 5–6 strong, 7+ mastered) and a large **Review due cards** button. Completing an atom enrolls it at bin 1 (`next_review_at` = now + 1d). Due cards (`next_review_at < now`) are reviewed with a random atom check; correct moves +1 bin, incorrect −2 (floor 1). Bin ≥ 7 sets `graduated_at` once; intervals are 1d / 2d / 4d / 1w / 2w / 3w / 4w, then +2w per bin (6w, 8w, …). See ADR 005.
- Each topic has at most one shared iconic image today (generate via AI or upload). One generation/upload produces a full (~1024) asset for the topic screen and a 512px JPEG thumb for hex tiles. The topic screen shows the square image above the title; the image button opens Generate / Upload (or Regenerate / Replace when an image already exists). Hex tiles fill with the thumb plus a scrim for title readability. Atom images use the same full/thumb pipeline and style prompt, plus the atom’s learn bit so the visual supports that atomic learning (`generate_pack_image` job).
- **Later (not built):** a topic may hold multiple visuals (gallery / testing variants) with one chosen primary for tiles and hero. Keep the single-image fields as the primary until that gallery lands.
- Each request stores hop distances and kinds for the returned neighborhood.
- User–topic interactions are appended to `user_topic_events` (per user): opening a neighborhood may write `focus` (server-side); intentional navigation writes `open` with `source` `graph` (canvas / trail taps), `search`, `list` (related topics on the topic screen), or `settings` (profile affinity badges). Cold-start resume does not record `focus` and never writes `open`. The Learn sheet records `learn`, `check1`, `check2`, and `check3` events with `pack_index` in the payload (checks include `correct` plus `choice_index` / `answer_bool` by type). Legacy `example` / free-text cloze `answer_text` events may still exist. This log is the basis for later trajectory and content generation; it does not replace `knowledge_requests` resume snapshots.
- One user–tile affinity measure with three per-user normalized factors (weights default 1), from **intentional opens only** (not `focus`, not cold-start): `interest_norm=open_count/Σ_tiles open_count`, `neighbor_norm=Σ_direct_neighbors open_count/same total` (both ∈ [0,1]), `recency` linear on last intentional open (today→1, ≥`AFFINITY_RECENCY_SPAN_DAYS`≈30d →0.5), then `affinity=w_interest*interest_norm+w_neighbor*neighbor_norm+w_recency*recency`. Learn/check/atom/`focus` events do not affect affinity (they still feed the learning track, `completed_packs`, and UI focus counts). Profile map (`GET /me/topic-affinity`) uses that score and clusters top topics by induced `knowledge_edges`. Cron jobs use the same affinity aggregated across users, plus a fill term: neighbor jobs `score=affinity+w_fill*(desired_neighbors−n)/desired_neighbors` (`CRON_NEIGHBOR_W_FILL`, `CRON_NEIGHBOR_BUDGET_TOTAL`=16); atom jobs `score=affinity+w_fill*(desired_packs−packs)/desired_packs` (`CRON_LEARN_W_FILL`, `CRON_LEARN_DESIRED_PACKS`=20). Collaborative filtering can later replace `affinity(u,t)` behind the same interface.
- Profile fields `username`, `full_name`, and `photo_url` live in `users.preferences.profile`. Uploaded avatars are stored as `users.photo_bytes` and served at `GET /me/photo` (`photo_url` is that API path). Learning XP/level on the HUD are placeholders until mastery tracking exists. Admins see the a-priori ranking queue (neighbors + atoms with affinity/fill/score) in App settings via `GET /admin/cron-runs/preview`; fill weights (`neighbor_w_fill` / `learn_w_fill`) are editable there and persist in `ranking_config` (env defaults until overridden). Each table has its own Run now that enqueues that queue and refreshes result columns.

## API

- `POST /api/v1/auth/firebase`
- `GET /api/v1/me`
- `PATCH /api/v1/me` `{username?, full_name?, photo_url?, display_name?, timezone?}`
- `GET /api/v1/me/photo` → JPEG bytes (auth)
- `PUT /api/v1/me/photo` multipart `file` → user payload with `photo_url`
- `DELETE /api/v1/me/photo`
- `GET /api/v1/me/preferences`
- `PATCH /api/v1/me/preferences`
- `POST /api/v1/me/events` `{events: [{node_id, kind, occurred_at?, payload?}]}` → `{recorded, ids}` (client `open` / learn / example / check; `open` payload `{source: graph|search|list|settings}`; `focus` may be written server-side on neighborhood open, not on cold-start resume)
- `GET /api/v1/me/topic-affinity?limit=24` → `{nodes, clusters, edges}` for the profile affinity map (each node: `rank`, `affinity`, `breakdown` `{interest,neighbor,recency}`)
- `GET /api/v1/me/learning-next?seed_node_id=` → `{status: ready, node_id, title, pack_index, pack, affinity, completed_packs, image_url, image_thumb_url, pack_image_url?, pack_image_thumb_url?}` or `{status: generate, node_id, title, image_url?, image_thumb_url?}` for the dice-picked tile when it has no unlearned atom. `image_url` / `image_thumb_url` are **effective** (atom override else topic). `opening=true` forces a focus-tile atom (unlearned preferred, else learned). `picked_node_id` sticks to that tile after a dice roll (prefetch waits on the same generate). Optional `exclude_node_id` + `exclude_pack_index` skip the on-screen atom for prefetch.
- `GET /api/v1/me/reviews/distribution` → Leitner bins `{distribution: [{bin, count, count_due, count_not_due}], due_count, graduation_bin, intervals_hours, first_next_review_at}`
- `GET /api/v1/me/reviews/due?limit=10` → `{items: [{node_id, title, pack_index, leitner_bin, pack, image_url?, image_thumb_url?, pack_image_url?, pack_image_thumb_url?}], due_count}`
- `POST /api/v1/me/reviews/submit` `{node_id, pack_index, correct, check_kind, choice_index?|answer_bool?|answer_text?}` → `{leitner_bin, next_review_at, graduated, updated}` (also appends a check event)
- `POST /api/v1/knowledge/bits/{bit_id}/feedback` `{rating: 1|-1|null}` → upsert/clear per-user thumbs on that quiz bit (`quiz_bit_feedback`)
- `GET /api/v1/knowledge/nodes/{id}/jobs` → active `expand_neighborhood` / `expand_content` / `generate_image` / `generate_pack_image` jobs for that node (any user); caller is attached as a watcher. Different job types may run in parallel; the same type coalesces across users (atom image by `pack_index`).
- `GET /api/v1/admin/cron-runs/preview` → a-priori ranked neighbor/learn queues with affinity, counts, fill term, score, live job result when a prior run enqueued that tile, and `limits` including `neighbor_w_fill` / `learn_w_fill` (403 unless `is_admin`)
- `PATCH /api/v1/admin/cron-runs/weights` `{neighbor_w_fill?, learn_w_fill?}` (≥0) → persist fill weights and return refreshed preview (403 unless `is_admin`)
- `POST /api/v1/admin/cron-runs/run` → enqueue ranking cron now (`queues`: `neighbors` and/or `learns`; default both; up to `CRON_*_JOBS_PER_DAY`, default 5 neighbor / 10 learn) and return `{run, preview}`; admin is attached as job watcher so jobs show in the progress float (403 unless `is_admin`)
- `DELETE /api/v1/admin/knowledge/nodes/{id}/packs/{pack_index}` → delete atom bits + related events + Leitner rows (403 unless `is_admin`)
- `DELETE /api/v1/admin/knowledge/nodes/{id}/packs/{pack_index}/bits/{kind}` → delete one quiz bit (+ events); last quiz returns 409 `CONFIRM_PACK_DELETE` unless `confirm_last_pack=true` (then deletes the atom)
- `POST /api/v1/knowledge/focus` `{topic?}` or `{node_id?}` → graph (200); with `expand: true` and under budget → `{job_id}` (202)
- `GET /api/v1/knowledge/nodes?q=` existing-topic autocomplete (no LLM)
- `GET /api/v1/knowledge/nodes/{node_id}/content` → `{pack_count, packs: [{pack_index, incomplete, title, bits, image_url?, image_thumb_url?, pack_image_url?, pack_image_thumb_url?}], completed_packs, incomplete}` (`completed_packs` = atom indexes where the user logged learn + any one check; `incomplete` when no atoms or any atom content-incomplete)
- `POST /api/v1/knowledge/nodes/{node_id}/content` `{expand?: bool, new_pack?: bool}` → content (200); with `expand: true` and missing/incomplete atom → `{job_id, pack_index}` (202); `new_pack: true` only when all atoms complete (else 422)
- `GET /api/v1/knowledge/nodes/{node_id}/image` → `{image_url, incomplete}`
- `POST /api/v1/knowledge/nodes/{node_id}/image` `{generate?, regenerate?}` → metadata (200) or `{job_id}` (202)
- `PUT /api/v1/knowledge/nodes/{node_id}/image` multipart `file` → metadata (200)
- `GET /api/v1/knowledge/nodes/{node_id}/image/file?variant=full|thumb` → PNG (full) or JPEG (thumb) bytes (auth)
- `GET /api/v1/knowledge/nodes/{node_id}/packs/{pack_index}/image` → atom-only `{image_url, incomplete}`
- `POST /api/v1/knowledge/nodes/{node_id}/packs/{pack_index}/image` `{generate?, regenerate?}` → metadata (200) or `{job_id, pack_index}` (202 `generate_pack_image`)
- `PUT /api/v1/knowledge/nodes/{node_id}/packs/{pack_index}/image` multipart `file` → metadata (200)
- `GET /api/v1/knowledge/nodes/{node_id}/packs/{pack_index}/image/file?variant=full|thumb` → PNG/JPEG bytes (auth)
- `DELETE /api/v1/knowledge/nodes/{node_id}` → delete topic + edges + atoms (+ pack images) + user events/reviews + job watchers for that node
- `GET /api/v1/knowledge/graph/{focus_id}` existing neighborhood only (no expand)
- `GET /api/v1/jobs/{job_id}`
- `GET /health`

Graph payloads use UUID ids. Node `kind` is `parent`, `sibling`, `child`, `related`, `extended` (neighbors of neighbors), or `focus`. Edge `type` uses the stored relation names. The canvas always shows every direct neighbor, then tops up with unique neighbors-of-neighbors (≤14) beside the direct they hang off toward 30 tiles including focus (grows past 30 only when directs alone require it). Only the focus node includes `description` and full `image_url`; every node may include `image_thumb_url` for tiles.

## Client

Edge-to-edge neighborhood canvas with a top-left profile HUD (avatar, level, name, XP bar). Tapping the HUD opens a profile overlay with Settings, Logout, a topic-affinity badge list under Learning about (one color per cluster from `GET /me/topic-affinity`; tap focuses that topic on the canvas), and a Practice placeholder. Settings is a Talivo-style sheet with App (appearance + AI provider), Profile (username, full name, photo upload), and Account (email/password) tabs. A small neutral search FAB opens a field above the keyboard and lists matching existing topics; tapping or submitting focuses that node on the canvas only. A second FAB above search opens the **testing track** (Leitner bins + Review due cards). Tapping the current focus tile starts the learning track (`open` from `graph`): one flip card (learn front, random check back), then a large Next continues with focus-relative dice picks (and background generate when needed). After each quiz answer, thumbs up/down sit left of Next/Done (learning + testing tracks) and persist on the shared quiz bit. Long-press on the **card** opens the atom action drawer (atom or topic image generate/upload; admins also delete quiz/atom). Long-press on a **hex tile** opens the topic action drawer (image, manage, relations, generate, **Show atomic learning** for the multi-atom review deck of that topic). Pulse placeholders run while an `expand_content` or atom-image job fills. Step/check events (including `pack_index`) go to `/me/events`. While a job runs, a lower-left chip shows live progress. TT Ramillas is used only on hex tile labels and search result titles; the rest of the UI uses the platform font.
