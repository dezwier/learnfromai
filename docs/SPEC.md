# Adaptive Mastery

Sign in, then explore one shared knowledge graph: Wikidata for hierarchy, Wikipedia for related topics.

## Product

- Authentication uses Firebase. The API exchanges a Firebase ID token for its own JWT.
- There is one item graph, shared by every signed-in user. A search does not create a private graph.
- An item is a Wikidata entity: stable Q number, title, optional description, and optional English Wikipedia title. Identity is the Qid.
- Hierarchy edges are typed: `subclass_of` (P279) or `parent_taxon` (P171). Related edges are `related_to` from Wikipedia morelike. The walk stops at these domain roots: Life (organism Q7239), physical world (Q223557), places (Q2221906), people (Q215627), organizations (Q43229), events (Q1190554), works (Q386724), knowledge (Q11862829), technology (Q11016), languages (Q34770), ideas (Q21484471).
- Searching a topic resolves it to a Wikidata item, then loads preferred parents (`up_depth`), direct children capped at eight by sitelinks (`down_depth`), and a related cloud (`cloud_radius`). Siblings are not auto-fetched. Wikimedia maintenance items are left out.
- Related topics come from Wikipedia `morelike` search, joined to Qids via `pageprops.wikibase_item`. Related nodes are not hierarchy-walked on that request. Limit is `8 * cloud_radius`.
- Nodes and edges are stored in PostgreSQL. A direction that was fully fetched inside the last 30 days is reused. An unfinished or stale direction is fetched again.
- The same node row is reused when another topic reaches it. Redirects are followed before upsert so merged items share one qid.
- Each request stores the shortest-path hop distance of every returned node to the focus. Distances belong to that request.
- Graph structure is not generated by a model. `POST /api/v1/graph/extend` responds 410.

## API

- `POST /api/v1/auth/firebase`
- `GET /api/v1/me`
- `GET /api/v1/knowledge/graph` (resume the signed-in user's latest focus)
- `GET /api/v1/knowledge/graph?topic=Dinosaurs&up_depth=1&down_depth=1&cloud_radius=1`
- `GET /api/v1/knowledge/graph?focus_qid=430&up_depth=1&down_depth=1&cloud_radius=1`
- `GET /api/v1/workspace/graph`
- `POST /api/v1/graph/extend` (retired; responds 410)
- `DELETE /api/v1/graph/extend/{request_id}`
- `DELETE /api/v1/graph/nodes/{concept_id}`
- `GET /api/v1/jobs/{job_id}`
- `GET /health`

`GET /knowledge/graph` returns `focus_node_id`, `incomplete`, `request_id`, `nodes`, and `edges`. Node ids are Wikidata Q numbers. `depth` is relative to the focus: negative above it, zero on it, positive below it. `distance` is the unsigned hop count to the focus. `kind` is `parent`, `focus`, `child`, or `related`. Edges include `type`. A search that has one clear head opens that item. Only a real tie returns 409 with `details.candidates` (`wikidata_qid`, `title`, `description`). No match returns 404. Defaults: `up_depth=1`, `down_depth=1`, `cloud_radius=1` (max depth/radius 2).

## Client

The Flutter app has a sign-in screen and a hierarchy canvas: parents above the focus, children below, pinch-pan only. Related topics sit in a horizontal strip under the map. Opening the app resumes the person's latest focus. Searching or tapping a node loads that qid. Loading uses `PulsePlaceholder` at map size.
